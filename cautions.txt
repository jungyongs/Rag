현재 준비하신 상태라면, GPU를 대여하기 전에 가장 중요하게 확인할 것은 학습이 중단되어도 복구할 수 있는지, GPU 대여 시간이 낭비되지 않도록 예외 상황을 처리할 수 있는지입니다.

특히 이번 CPT(Continued Pretraining)는 학습 시간이 길고 체크포인트 크기가 클 수 있으므로, 단순히 학습 코드가 돌아가는 것보다 중단·복구·저장·모니터링까지 갖춘 상태로 시작하는 것이 좋습니다.

## 1. 중단 및 복구 관련

| 항목           | 준비해야 할 내용                                         | 중요도 |
| ------------ | ------------------------------------------------- | --- |
| 체크포인트 자동 저장  | 일정 Step마다 모델과 학습 상태 저장                            | 필수  |
| 체크포인트 버전 관리  | 최신 체크포인트를 무조건 덮어쓰지 않고 최근 2\~3개 유지                 | 필수  |
| 학습 재개 기능     | 중단 이후 마지막 정상 체크포인트부터 재개                           | 필수  |
| 학습 상태 전체 저장  | 모델 가중치뿐 아니라 Optimizer, Scheduler, RNG, 학습 Step 저장 | 필수  |
| 비정상 종료 대응    | 서버 재시작, OOM, 강제 종료에 대비                            | 필수  |
| 체크포인트 복구 테스트 | 실제로 저장 → 종료 → 재시작해 정상 복구되는지 검증                    | 필수  |
| 자동 재시작       | 서버 환경이 지원하면 비정상 종료 시 자동 재제출하도록 구성                 | 권장  |

### 특히 주의할 사항

① 최신 체크포인트 하나만 덮어쓰는 것은 추천하지 않습니다.

저장 도중 서버가 종료되면 유일한 체크포인트까지 손상될 수 있습니다.

대신 다음과 같은 구조가 안전합니다.

```
checkpoints/
├── checkpoint-1000/
├── checkpoint-1500/
└── checkpoint-2000/  ← 최신 정상 저장본
```

새로운 체크포인트 저장이 완료된 후 가장 오래된 것을 삭제하는 방식입니다. Hugging Face Trainer를 사용한다면 `save_total_limit`으로 보관 개수를 제한할 수 있습니다.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://github.com\&sz=32)

+1



② 모델 가중치만 저장하면 완전한 학습 재개가 아닙니다.

예를 들어 3,000 Step에서 중단되었을 때, 모델 가중치만 불러오면 Optimizer와 Learning Rate Scheduler가 초기화되어 학습 흐름이 달라질 수 있습니다.

체크포인트에 전체 상태가 저장되는지 확인해야 합니다.&#x20;

③ 저장 기능보다 복구 테스트가 중요합니다.

GPU 대여 후 본격적인 학습에 들어가기 전에 짧은 학습을 실행하고, 체크포인트를 저장한 뒤 종료하여 이어서 정상 학습되는지 반드시 확인해야 합니다.

## 2. 서버 실행 및 연결 종료 관련

| 항목              | 준비해야 할 내용                                       | 중요도 |
| --------------- | ----------------------------------------------- | --- |
| 서버 내부 독립 실행     | SSH 또는 로컬 컴퓨터 연결이 끊겨도 학습 유지                     | 필수  |
| Docker 백그라운드 실행 | Docker를 사용하는 경우 컨테이너 내부 학습이 로컬 터미널에 종속되지 않도록 구성 | 필수  |
| 학습 로그 파일 저장     | 터미널을 닫아도 학습 로그가 서버에 남도록 설정                      | 필수  |
| 서버 재부팅 대응       | 서버 재부팅 또는 컨테이너 재생성 후 학습을 복구할 수 있도록 구성           | 필수  |
| 학습 상태 원격 확인     | SSH 재접속 또는 대시보드로 진행 상태 확인                       | 권장  |
| 종료 신호 처리        | 서버가 정상 종료 신호를 보낼 때 체크포인트 저장 시도                  | 권장  |

실행 환경에 따라 방법이 다릅니다.

- 일반 GPU 서버: `tmux` 또는 `systemd` 등을 통해 SSH 연결과 독립적으로 실행
- Docker 서버: 백그라운드 컨테이너 실행 및 로그 저장
- Slurm 기반 GPU 클러스터: `sbatch`로 학습 작업 제출

주의할 점은 `tmux`나 Docker 백그라운드 실행만으로는 서버 자체의 재부팅, 컨테이너 삭제, GPU 대여 기간 종료에 대응하지 못한다는 것입니다.

따라서 GPU 제공 측에 서버 종료 시 실행 중인 작업과 저장된 데이터가 어떻게 처리되는지 확인해야 합니다.

## 3. 데이터 및 저장 공간 관련

이 부분은 GPU를 빌리기 전에 최대한 해결해야 합니다. 특히 모델을 미리 다운로드해서 Mount할 예정이라면 어떤 저장소에 무엇을 저장하는지가 중요합니다.

| 항목          | 준비해야 할 내용                                  | 중요도 |
| ----------- | ------------------------------------------ | --- |
| 저장소 영속성 확인  | GPU 서버가 종료되어도 체크포인트와 로그가 유지되는 저장소 확보       | 필수  |
| 저장 공간 용량 확인 | 모델 + Optimizer 상태 + 체크포인트 2\~3개 + 로그 용량 계산 | 필수  |
| Mount 경로 확인 | 모델, 데이터, 출력 디렉터리가 컨테이너에서 정상 접근되는지 확인       | 필수  |
| 데이터 무결성 검증  | 전송 전후 파일 개수·크기·SHA-256 해시 비교               | 필수  |
| 데이터 로딩 테스트  | 전체 데이터를 읽을 수 있는지, 손상되거나 비어 있는 샘플이 없는지 검증   | 필수  |
| 학습 데이터 토큰화  | 미리 토큰화 및 Sequence Packing을 수행할 수 있는지 검토    | 권장  |
| 체크포인트 외부 백업 | GPU 서버와 독립된 스토리지에 정상 체크포인트 주기적 복제          | 권장  |
| 디스크 부족 대응   | 용량 부족 시 체크포인트 저장 실패를 탐지하도록 구성              | 필수  |

여기서 가장 중요한 것은 Mount했다고 해서 데이터가 영구 보존되는 것은 아니라는 점입니다.

Docker 컨테이너 내부 파일은 컨테이너 삭제 시 사라질 수 있습니다. 따라서 체크포인트는 영속 스토리지에 연결된 경로에 저장해야 합니다.&#x20;

## 4. 학습 환경 및 GPU 관련

| 항목                 | 준비해야 할 내용                                                                    | 중요도 |

| GPU·CUDA 호환성 확인    | 대여 GPU의 드라이버와 CUDA/PyTorch 버전 호환성 확인                                         | 필수  |

| 분산학습 오류 대응         | NCCL 통신 문제, GPU 일부 미인식, 프로세스 Hang 등에 대한 점검 방법 준비                             | 필수  |

CUDA 런타임, 드라이버, 일부 CUDA 확장 라이브러리는 실제 GPU 서버에서 최종 호환성 확인이 필요합니다.&#x20;

## 5. 학습 진행 중 오류 탐지 및 모니터링

| 항목           | 준비해야 할 내용                                       | 중요도 |
| ------------ | ----------------------------------------------- | --- |
| Loss 모니터링    | Loss가 NaN/Inf가 되거나 비정상적으로 급증하는 상황 감지            | 필수  |
| GPU 사용률 모니터링 | GPU Utilization, VRAM, 전력 및 온도 확인               | 필수  |
| 학습 속도 기록     | Tokens/sec, Steps/sec, Step별 소요 시간 기록           | 필수  |
| 디스크 사용률 모니터링 | 체크포인트 저장 공간이 부족해지기 전에 감지                        | 필수  |
| 학습 정체 탐지     | 프로세스는 살아 있지만 Step이 증가하지 않는 상황 탐지                | 필수  |
| 학습 로그 영구 저장  | Loss, Learning Rate, Step, 처리 토큰 수, 오류 내역 보존    | 필수  |
| 오류 알림        | 학습 종료, 실패, Loss 이상, 디스크 부족 시 알림                 | 권장  |
| 주기적 검증 평가    | 별도 Validation Set의 Loss/Perplexity를 통해 학습 상태 확인 | 권장  |

CPT에서는 Training Loss가 감소하는 것만으로 모델이 정상적으로 개선되고 있다고 보장할 수 없습니다.

따라서 학습하지 않은 의료 텍스트 Validation Set을 미리 구성해 두고, 같은 조건에서 주기적으로 평가하도록 준비하는 것이 좋습니다.

## 6. 학습 설정 및 실험 재현성

이 부분은 GPU 대여 전에 거의 모두 완료할 수 있습니다.

| 항목                      | 준비해야 할 내용                                              | 중요도 |
| ----------------------- | ------------------------------------------------------ | --- |
| 학습 Config 확정            | Learning Rate, Batch Size, Sequence Length, Epoch 등 확정 | 필수  |
| 총 학습량 계산                | 전체 토큰 수 기반으로 Total Steps, Tokens Seen 산정               | 필수  |
| Effective Batch Size 계산 | GPU 수 × Micro Batch Size × Gradient Accumulation 계산    | 필수  |
| 토크나이저 검증                | 특수 토큰, EOS, Padding, Attention Mask, Labels 확인         | 필수  |
| 데이터 분할 고정               | Train/Validation 분할 확정 및 중복·누출 방지                      | 필수  |
| 학습 재현성                  | Random Seed, 데이터 순서, 학습 설정, 코드 버전 기록                   | 필수  |
| Resume 시 설정 일관성         | 중단 후 재시작 시 모델 구조·토크나이저·학습 설정 등이 호환되는지 확인               | 필수  |
| CPU 기반 테스트              | 작은 더미 모델과 소량 데이터로 데이터 처리·학습 루프·저장 로직 테스트               | 필수  |
| 학습 완료 후 내보내기            | 최종 모델·토크나이저·Config 저장 및 추론 로딩 테스트 준비                   | 필수  |

특히 총 학습량을 계산할 때는 데이터 파일 개수가 아니라 토큰 수를 기준으로 잡는 것이 중요합니다.

CPT 학습량은 다음 관계로 계산할 수 있습니다.

\\[ \text{Total Steps} \approx \frac{\text{학습할 총 토큰 수}} {\text{GPU 수}\times\text{Micro Batch}\times\text{Accumulation}\times\text{Seq Length}} \\]

단, 이는 모든 Sequence가 지정 길이로 채워지는 경우의 근삿값입니다. Packing 효율이나 마지막 Batch 등에 따라 달라질 수 있습니다.

## 7. GPU 제공 측에 사전 확인할 사항

기술적으로 준비하더라도 서버 운영 정책 때문에 문제가 발생할 수 있습니다.

| 확인할 사항    | 질문할 내용                                                   |
| --------- | -------------------------------------------------------- |
| GPU 대여 시간 | 예약 시간이 끝나면 작업이 즉시 종료되는가?                                 |
| 종료 사전 알림  | 종료 전에 신호를 받을 수 있는가?                                      |
| 데이터 보존    | GPU 대여 종료 이후에도 체크포인트와 데이터가 유지되는가?                        |
| 외부 저장소    | GPU 서버에서 다른 워크스페이스 또는 S3 등에 접근할 수 있는가?                   |
| Docker 권한 | Docker 실행 및 필요한 Mount 설정이 가능한가?                          |
| 학습 실행 정책  | `tmux`, Docker 백그라운드 실행, Slurm Batch 작업 중 무엇을 사용할 수 있는가? |
| 하드웨어 구성   | 실제 GPU 종류·개수·VRAM, CPU RAM, 스토리지 용량 및 속도는 얼마인가?          |
| 네트워크      | 내부 노드 간 GPU 통신과 외부 데이터 전송에 제한이 있는가?                      |
| 장애 대응     | 서버 장애 발생 시 재대여 또는 작업 복구가 가능한가?                           |
